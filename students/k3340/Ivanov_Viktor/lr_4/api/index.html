    Взаимодействие фронта с API (подробно)¶

    В ЛР4 фронтенд (Vue) — это SPA, которая общается с бэкендом ЛР3 (DRF) по HTTP и получает/отправляет JSON.

    1) Базовая схема¶

    1.1 Базовый URL¶

    Все запросы идут на бэкенд ЛР3, который в локальном режиме запускается на:

    • http://127.0.0.1:8002

    Фронтенд обращается к API по префиксу /api/..., например: - GET http://127.0.0.1:8002/api/students/ - POST http://127.0.0.1:8002/api/grades/

    1.2 Где формируются запросы на фронте¶

    • Единый HTTP‑клиент (axios): frontend/src/services/api.js
    • задаёт baseURL
    • выставляет заголовки по умолчанию

    • добавляет токен авторизации в каждый запрос (interceptor)

    • Авторизация (Pinia store): frontend/src/stores/auth.js

    • register(), login(), logout(), fetchMe()

    • CRUD‑страницы: frontend/src/views/*.vue

    • load() (GET список)
    • save() (POST/PATCH)
    • removeItem() (DELETE)

    2) Заголовки и формат данных¶

    2.1 JSON по умолчанию¶

    Фронт просит и отправляет JSON: - Accept: application/json - Content-Type: application/json

    Это важно в DEBUG‑режиме Django: если сервер возвращает HTML‑страницу ошибки, фронт показывает сообщение об ошибке.

    2.2 Авторизация через токен¶

    Бэкенд использует Djoser TokenAuth. После входа фронт хранит токен и подставляет его в запросы:

    • Authorization: Token <token>

    Если токена нет — большинство эндпоинтов вернёт 401: «Учетные данные не были предоставлены.»

    3) Авторизация (Djoser) — какие запросы идут¶

    3.1 Регистрация¶

    • POST /api/auth/users/

    Тело запроса (пример):

    {
  "username": "user1",
  "email": "user1@mail.com",
  "password": "qwerty123",
  "re_password": "qwerty123"
}

    3.2 Вход¶

    • POST /api/auth/token/login/

    Тело (пример):

    {
  "username": "user1",
  "password": "qwerty123"
}

    Ответ:

    {
  "auth_token": "..."
}

    3.3 Профиль¶

    • GET /api/auth/users/me/ (с Authorization: Token ...)

    3.4 Выход¶

    • POST /api/auth/token/logout/

    4) CRUD‑паттерн (как формируются GET/POST/PATCH/DELETE)¶

    Практически во всех страницах CRUD одинаковый шаблон:

    4.1 GET (получить список)¶

    Пример: - api.get('/api/classrooms/?limit=200')

    Ответ — массив объектов (у вас часто без пагинации). Фронт кладёт данные в items и отображает таблицей v-data-table.

    4.2 POST (создать)¶

    Пример: - api.post('/api/classrooms/', payload)

    Где payload — объект из формы (edited), который собирается через v-model.

    После успешного POST: - закрыть диалог (dialog=false) - обновить список (await load())

    4.3 PATCH (редактировать)¶

    Пример: - api.patch('/api/classrooms/<id>/', payload)

    На фронте переключение POST/PATCH обычно делается по наличию edited.id: - если edited.id есть → PATCH - если нет → POST

    4.4 DELETE (удалить)¶

    Пример: - api.delete('/api/classrooms/<id>/') и затем await load().

    5) Read‑only и Write‑only поля (важный момент)¶

    Иногда бэкенд отдаёт “красивое” поле для отображения, но для записи ожидает другое.

    Пример: учителя и кабинет¶

    В API учителя: - assigned_room — объект (read‑only) с номером кабинета - assigned_room_id — id (write‑only) для POST/PATCH

    Поэтому фронт: - в таблице читает assigned_room.number - в форме отправляет assigned_room_id

    6) Эндпоинты и поля по страницам (что отправляется/принимается)¶

    Ниже перечислены основные страницы и соответствующие им API.

    6.1 Кабинеты (Classrooms)¶

    • GET /api/classrooms/
    • POST /api/classrooms/
    • тело: { number, title, category, capacity }
    • PATCH/DELETE /api/classrooms/{id}/

    6.2 Предметы (Subjects)¶

    • GET /api/subjects/
    • POST /api/subjects/
    • тело: { code, name, category, description }
    • PATCH/DELETE /api/subjects/{id}/

    6.3 Классы (Classes)¶

    • GET /api/classes/
    • в ответе есть homeroom_teacher_name (read‑only) для отображения
    • POST /api/classes/
    • тело: { title, grade_level, profile, homeroom_teacher }
    • PATCH/DELETE /api/classes/{id}/

    Важно: удаление класса может быть запрещено, если в нём есть ученики (на бэке Student.school_class = PROTECT). В интерфейсе показывается предупреждение.

    6.4 Учителя (Teachers)¶

    • GET /api/teachers/
    • в ответе assigned_room — объект
    • POST /api/teachers/
    • тело: { first_name, last_name, middle_name, email, phone, assigned_room_id }
    • PATCH/DELETE /api/teachers/{id}/

    6.5 Ученики (Students)¶

    • GET /api/students/
    • в ответе есть class_title (read‑only) — название класса
    • POST /api/students/
    • тело: { first_name, last_name, middle_name, gender, school_class, is_active }
    • PATCH/DELETE /api/students/{id}/

    6.6 Расписание (Schedule)¶

    • GET /api/schedule/
    • в ответе есть class_title, subject_name, teacher_name, room_number
    • POST /api/schedule/
    • тело: { school_class, subject, teacher, room, weekday, lesson_number }
    • PATCH/DELETE /api/schedule/{id}/

    6.7 Оценки (Grades)¶

    • GET /api/grades/
    • в ответе есть student_name, subject_name, graded_by_name
    • POST /api/grades/
    • тело: { student, subject, quarter, value, graded_by, comment }
    • PATCH/DELETE /api/grades/{id}/
